10Technical architecture

The structure below suits any cross-platform or fully native app: one rules engine decides, and thin native code on each platform applies the decision.

One shared engine (pure TypeScript functions that tests can run across time zones and daylight saving) decides what is blocked and why: lock times, daily limit, earned time, focus, strictness, unlocks and pending changes. The store keeps rules and 14 days of history on the device and sends a plan to native code on app open, resume, rule change and after earning; native reports merge back. The bridge is small: isSupported, requestAuthorization, pickApps, sync(plan), takeState(), takeUnlock, stopAll. App lists travel inside the plan, so changing them follows the strictness rules.

Expo notes: Expo Go can't run this; a development build is required. The iOS extensions are generated from config (@bacons/apple-targets), never by editing ios/, and sit behind a build flag so free Apple teams can still build. react-native-device-activity covers similar ground on iOS [112]; Foqos is an open-source native example [113]. Extensions stay tiny: no JavaScript runtime, database or network.

10.1 Safe removal and interrupted sessions

  1. No block without an end. Every focus, unlock and lock-time edge is registered with the system.
  2. A hard cap on focus length (3 h), so a bad input can't lock someone out for a day.
  3. Reconcile on every app open: recompute from the rules and clock, clear anything expired, re-register schedules. This also repairs schedules that reportedly vanish until the app is opened [29].
  4. An emergency path sized by strictness (M8), and an always-allowed list.
  5. An explicit "Turn off" that clears every store before the user deletes the app, because what happens to shields after deletion is undocumented [30].
  6. Protection lost: record the gap in history, show a red banner, and offer to re-grant.
